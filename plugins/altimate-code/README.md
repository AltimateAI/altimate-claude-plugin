# Altimate Code — Claude Code plugin

Gives Claude Code direct access to the model-free data tools of [altimate-code](https://github.com/AltimateAI/altimate-code), an open-source CLI with 100+ deterministic data-engineering tools: column-level lineage and impact analysis, PII detection, data-diff and parity, FinOps and query cost, query equivalence, dialect translation, and queries and schema inspection on connected warehouses.

**Why call the tools directly?** Claude reasons, the tools compute. Neither the MCP server nor `altimate tool run` runs a second LLM, so there is no second agent's model to pay for: on workspace questions this cost 12% less per run than delegating, at the same accuracy (benchmark in the PR that introduced it). Long multi-step jobs (dbt builds, migrations) can still be delegated with `altimate run`.

**Two modes, one set of tools.**

| Mode | When | How |
|---|---|---|
| MCP | The session has the plugin's MCP tools (`mcp__plugin_altimate-code_altimate-code__*`) | Claude calls them directly. The plugin's `.mcp.json` runs `altimate-code mcp serve`, read-only by default. |
| CLI | The MCP tools are not available | Claude runs `altimate tool context` once, then `altimate tool run <name> --args '<json>'` through Bash. |

The CLI mode is what keeps the plugin useful for an organisation that disallows MCP servers through managed settings (for example `allowedMcpServers` or `deniedMcpServers`): the plugin's server is then not started, and Claude uses the same tools through the shell. When the server fails to start or the installed build has no `mcp serve`, the session stays in the MCP mode without the routing guidance, and the skill still falls back to `tool run`. At session start the plugin decides which mode applies without starting the CLI: the CLI mode when `altimate-code` is not on PATH, a `managed-mcp.json` is present, settings deny the server (`deniedMcpServers`, or `allowedMcpServers` that admits neither its name nor its command, read as Claude Code merges them, including `managed-settings.d/` and `allowManagedMcpServersOnly`) or it was turned off in `/mcp` for the project, otherwise MCP. Policies delivered only by an MDM profile or the Windows registry are not read; set `ALTIMATE_DATA_MODE=cli` there (`ALTIMATE_DATA_MODE=cli|mcp` overrides). In the CLI mode it also adds the project routing guidance to the session, so the project's `CLAUDE.md` does not need it; `altimate-code link --claude-md` can still write it there for other clients. The MCP mode adds no routing guidance.

## Install

```bash
claude plugin install altimate-code --marketplace AltimateAI/altimate-claude-plugin
```

## Update

```bash
claude plugin marketplace update altimate-claude-plugin
claude plugin update altimate-code@altimate-claude-plugin
```

Then restart Claude Code.

## Prerequisites

The altimate-code CLI must be installed and configured on your PATH, version 0.12.11 or later. Older releases give no column answer, so the end-of-task summary and report can't say which columns a change reaches. Install it with npm:

```bash
npm i -g @altimateai/altimate-code   # requires Node 20+; exposes `altimate` and `altimate-code`
altimate                             # launch the TUI, then run /connect to configure your LLM provider
```

At session start the plugin checks the version on PATH. An older or missing altimate-code stays on the status line, with the binary, its path and this install command.

The CLI mode invokes `altimate`, the CLI's canonical name, and falls back to `altimate-code` for npm installs older than v0.7.1, so standalone installs work without an alias.

**MCP mode and the CLI name.** The MCP registration launches `altimate-code mcp serve`. npm, Homebrew and current curl and PowerShell installs expose both names, but curl and PowerShell installs older than v0.12.8 expose only `altimate`: there the server cannot start until `altimate-code` is on PATH (for example `ln -s "$(command -v altimate)" ~/.local/bin/altimate-code`), and Claude uses the CLI mode meanwhile. MCP mode also needs a build that contains `mcp serve`; check with `altimate-code mcp serve --help`. Direct MCP and `tool run` need no LLM provider; only delegation (`altimate run`) does.


Or configure a provider via environment variable (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, and 20+ others — see the [altimate-code docs](https://docs.altimate.sh)).

If altimate-code is not on PATH or not configured, the plugin surfaces the failure with fix instructions rather than silently falling back to Claude's native tools.

## How it works

1. A **SessionStart hook** adds a description of the available tools and both modes to the session, and copies the linked workspace's skills (see below). It does not start the MCP server. In a linked project, the [team rules](#team-rules) hooks add the workspace's rules too.
2. **MCP mode.** Claude calls `warehouse_list`, `warehouse_add`, `sql_execute` (`tables` returns columns and value profiles; large results spill to a local file), `sql_materialize` (session-local `scratch` DuckDB for cross-database joins), `answer_commit`, and `impact_analysis`, `dbt_lineage`, `altimate_core_column_lineage`, `schema_detect_pii`, `data_diff`, `altimate_core_equivalence`, `sql_translate`.
3. **CLI mode.** The **skill** has Claude run `altimate tool context` once (connections, schema listing, analyst method), then `altimate tool run <name> --args '<json>'` through Bash and reason over the structured output. `altimate tool list --json` shows every tool and its input schema. A warm process per project starts automatically.
4. Calls are read-only unless you approve `--allow-write` (CLI mode), except the project health check: it runs `dbt_health` with write, without asking, because the dbt project's integration refreshes `target/` (and runs `dbt deps`), so it starts only in an interactive session (or with `healthBlocksPush` on) that is inside a dbt project, and has no separate off switch; `DROP DATABASE`, `DROP SCHEMA` and `TRUNCATE` are always blocked. Read-only is enforced by the database on Postgres, SQLite and DuckDB and by SQL classification elsewhere, so use a read-only DB user for the strongest boundary.
5. For long multi-step jobs, or when you invoke **`/altimate-code:altimate <task>`** for work that needs the agent, Claude Code runs `altimate run "<your task>"` locally with the `builder` agent (or `analyst` for a data question when MCP is unavailable), which uses your configured LLM provider.
6. Warehouse queries and dbt commands run **locally under your credentials**. If the installed CLI predates the `tool` subcommand, the skill falls back to delegation.

Connections come from project and global `.altimate-code/connections.json` files and `ALTIMATE_CODE_CONN_*` environment variables. To pin a file for the MCP server, change the `args` in `.mcp.json` to `["mcp", "serve", "--workspace-tools", "--connections", "/absolute/path/to/connections.json"]`.

### Optional: route warehouse queries to the tools

Set `ALTIMATE_ROUTE_GUARD=1` to enable a PreToolUse hook that denies Bash commands querying a warehouse directly (`psql -c`, `trino --execute`, `docker exec ... clickhouse-client`, `snowsql`, `bq query`) and suggests the matching `tool run`. It is off by default and a best-effort nudge, not a security control: it never blocks a lone `altimate` command, dbt, or file operations, while `altimate` chained with other commands is checked like any command. Quoted text (a commit message, say) is never taken as a command, but a `$(...)` or backtick substitution inside it is. It needs `python3`; without it every command is allowed.

### Optional: analyst agent

`claude --agent altimate-code:analyst` starts a read-only data analyst that answers questions through the MCP tools when present and `tool run` otherwise, and ends with a `FINAL ANSWER:` line.

## Use an Altimate workspace

An [Altimate workspace](https://help.altimate.ai/workspaces/) holds your team's shared skills, knowledge, memory and warehouse integrations. Claude reaches the workspace linked to the project directly, with three tools that run no model of their own (knowledge questions are answered by Altimate's backend models) and work the same over MCP and through `altimate tool run --workspace-tools`:

- `workspace_context` reports whether sign-in or linking is needed, and once linked gives the workspace summary, skill names, bounded project memory and (with `include_tools`) the knowledge and warehouse operations available.
- `workspace_skill` reads one shared skill.
- `workspace_execute` runs one of those operations: `ask_knowledge_base`, listing the workspace's warehouse connections, or a read-only query on them. Writes are refused.

Claude does the reasoning; no altimate-code agent runs. Knowledge questions are answered by Altimate's backend. Each call carries a workspace receipt from `workspace_context`, so a change of account or link is detected before anything runs. Workspace tools need an altimate-code build with the `tool` CLI and `--workspace-tools`; with an older CLI, workspace questions are delegated to altimate-code, which uses the workspace automatically.

1. **Sign in to Altimate** — `altimate auth login -p altimate-backend --method "Altimate LLM Gateway"` (`altimate-code` on npm installs older than v0.7.1). It opens your browser. This also sets up the model provider altimate-code uses. You can run it from Claude Code by typing it after `!`.
2. **Link the project** — ask Claude to link the project to your workspace. It shows the workspaces `workspace_context` (or `altimate workspace list`) returns and links the one you choose with `altimate link --workspace "<id or name>"`, or creates one with `altimate link --create`. Claude links with `ALTIMATE_DISABLE_MEMORY=1`, so existing memory on this machine is not uploaded. Moving a linked project to a different workspace also needs `--yes`. `workspace list` is in newer altimate-code releases; with an older one, tell Claude the workspace's name. In a terminal, `altimate link` does the same with a picker; the picker does not work after `!` in Claude Code.
3. **Check it** — `altimate workspace status` shows the linked workspace, how much memory has reached it and when its skills last synced.
4. **Ask Claude** — questions about your team's conventions, definitions or knowledge, and queries on the workspace's warehouses, use the workspace tools: *"How do we define recurring revenue?"*, *"Which Snowflake connections does our workspace have?"* Start a request with `/altimate-code:altimate` to be sure it does.
5. **Workspace engine** — knowledge and warehouse operations need the workspace engine. If it is missing, Claude asks before installing it with `altimate workspace-client engine-install` (Node.js 20+ and npm).

**Team skills as Claude Code skills.** In both modes, session start copies the linked workspace's skills into the project's `.claude/skills/`, so they load like any project skill. Copies keep only each skill's name and description from the frontmatter, have `!` command blocks neutralised and are served only for the Altimate account you are signed in to. A skill you wrote with the same name is never replaced or removed (to customise a team skill, copy its folder under a new name and delete the `.altimate-workspace-skill` file in the copy), and the copies are kept out of git. A project that was not synced, or not attempted, for an hour is refreshed in the background (`altimate workspace refresh`); the skills show up when it finishes. Set `ALTIMATE_CLAUDE_SKILL_SYNC=0` to turn the copy off; the next session start then removes the copies. The altimate CLI copies skills only when the plugin's refresh asks it to, so this one setting covers both. Uninstalling the plugin leaves them in place: delete the `.claude/skills/` folders that contain `.altimate-workspace-skill`.

**Skills and memory.** Ask Claude to list skills (`altimate skill list`), pull the latest (`altimate workspace refresh`) or share a project skill you name (`altimate skill publish <name>`; replacing needs your confirmation). Claude saves a memory to the workspace only when you ask, after showing you the workspace, id and text, with `altimate workspace-client remember`. What altimate-code learns during delegated `run` tasks is saved to the workspace's memory as before.

## One-click integrations

The plugin finds GitHub, Jira and Linear credentials you already have and connects them without retyping them:

- `gh`, jira-cli and Linear credentials on this machine, and GitHub, Atlassian or Linear MCP servers configured in Claude Code, are detected when a session starts.
- A band above the prompt offers **Connect**, **Keep local**, **Review** or **Later** for what it found, and shows **Token rejected · Update** when a saved token stops working. The status line shows how many integrations are connected.
- `/integrations` opens a side pane with one row per provider. **Add credentials** (or **Update**) opens a short form: type the non-secret fields, then **Create token ↗** opens the provider's token page and **Paste from clipboard** stores the token (shown masked afterwards). **Connect & sync** saves it, **Keep local** saves it without syncing, **Cancel** discards the form.
- A connected row offers **Sync**, **Allow sync** (after Keep local) and **Disconnect**. In a folder not linked to a workspace, **Link workspace** lists your workspaces and links the one you pick. When you are not signed in to Altimate, everything works locally: **Connect** and **Connect & sync** are not shown (use **Keep local**), the sync buttons are hidden, and the band and pane offer **Sign in to sync**, which opens the browser sign-in on that click only.
- **Keep local** blocks syncing for that provider: the credential stays in your OS keychain and is never sent to Altimate, not even by **Link workspace** or **Sync all**, until you press **Allow sync**. For a provider that is not kept local, **Link workspace** and **Sync all** upload nothing over a connection this tool already made in your workspace: they only attach it to the linked workspace, also when this machine has no record of it, unless the workspace marks it invalid. A connection saved to your workspace has no local copy, so its row has no **Keep local** button of its own. Open **Update**: the form also offers **Keep local** (paste the token again), and pressing it removes the workspace connection this tool made and keeps the credential here. **Disconnect** followed by **Add credentials** with **Keep local** does the same. If the workspace cannot be read, Keep local is refused with the reason and nothing is moved or removed. If the credential is kept on this machine but the workspace copy could not be removed, a warning says so; remove it in the workspace. A credential checked while the provider is unreachable is kept only with **Keep local**, marked not verified yet. **Disconnect** says when the connection could not be taken off the linked workspace. A token the provider or the workspace rejects is not kept: a new connection the workspace marks invalid is removed again, and an update it rejects leaves the existing connection marked rejected. For a credential saved to the workspace the row shows the most recently validated connection; a credential kept on this machine is shown as stored here. **Update** and **Disconnect** act on the one this tool made. A clipboard holding a URL is not taken as a token. **Sync** and **Sync all** test the credential with its provider first and upload nothing when it is rejected or the provider cannot be reached. On macOS a secret that cannot be written to the keychain is not stored at all, never written to a file.

The side pane and band need a Claude Code build with hooks modules and `altimate integrations` from altimate-code.

## Lineage beside the chat

The plugin's lineage pane follows the dbt model Claude reads or edits (by Read, Edit, a shell command that names or finds its `.sql` file, or a `dbt_lineage` call), read from `target/manifest.json` with no model calls. The end-of-task summary's **Open lineage** opens it too. A project with no manifest still gets its graph, read from the models' `ref()` and `source()` calls; columns, dashboards and column reach then need `dbt parse` or `dbt compile`. From a monorepo's root, `/lineage <model>` finds the dbt project below it that has the model:

- **The graph.** The model's whole lineage as boxes and arrows, like dbt-lineage-viewer: every level upstream on the left and downstream on the right, every model, every name in full, dashboards (exposures) marked ◆. The pane is a window onto the drawing. A graph too big for Claude Code to draw in a pane is shown as folders instead, and the header says so; `v` switches to the other views. Scroll it up and down with the mouse, touchpad or arrow keys, pan it with `h` and `l` (or ◀ ▶), and `f` brings the model back to the middle. Links between models on the same level, or that skip a level, are not drawn. Press a model to follow it. With a column picked, the models and dashboards that read it are highlighted and the rest dimmed.
- **Views for big projects.** `v` cycles the graph, **ends only** (the sources and dashboards the model sits between; "via N" counts the models between them on the shortest path), **folders** (sources, staging, intermediate, marts and dashboards as one box each, with counts, in dbt layer order: a source-to-mart chain on one screen) and the text **list** of upstream and downstream. A pane narrower than 48 columns shows the list. The pane keeps up to 500 models upstream, and through altimate-code (a manifest over 4 MiB) up to 500 downstream too; past that the header says which side was cut.
- **What the answer is about.** Once the session has seen a dbt project, after each answer the models Claude named are listed under the header (IN THE ANSWER), each a press away. When Claude answered without reading any model that turn (from what it read earlier), the pane follows the first model it named, so the lineage shown matches the answer.
- **Columns.** Each output column with its source columns and how it is derived, from altimate-code's `dbt_lineage`, read from the compiled manifest (`dbt compile`). The plugin's calls are read-only, so altimate-code never starts the project's dbt adapter for them.
- **Column reach.** `c` picks a column; the pane shows the downstream models whose SQL reads it and the dashboards on them, from `impact_analysis` (it traces each downstream model's compiled SQL, renames included). Models that name the column only in a filter or join, or that could not be traced (no compiled SQL), are listed apart, and the count is then a lower bound.
- **Impact first.** Before an edit to a model's SQL lands, the plugin checks what reads the model and the reach of every column the edit touches (up to three, merged). It tells a touched column from the model's own lineage (what the pane already read, or `dbt_lineage` through the CLI), so a column `schema.yml` leaves out still counts. It adds the result to Claude's context with the edit's result. You see the summary at the end of the task, not a note per edit; a toast says so when the lookup missed its time or failed and the edit went ahead without it.
- **End-of-task summary.** When a task (one prompt and Claude's work on it) changed a model, by an edit or a shell command git sees, a band above the prompt says what changed and how far it reaches: each changed column (up to three per model) with the columns, models and end columns downstream that carry its value, and how many more models may change, next to the model-level count, and a line when some models could not be read. The trace reads a copy of `target/manifest.json` taken when the task started, so a recompile mid-task does not change the answer. These lookups go through the CLI, so they raise no permission prompt.
- **The report, on demand.** **Open report** or `/lineage-report` builds an offline HTML report of the last task that changed a model and opens it in the browser (`target/.altimate-lineage/report.html`). It leads with what changed, before and after, what to expect downstream in plain words, and who consumes it: the dbt exposures on the model or downstream, grouped by whether they read a model the value reaches, and a plain statement when the project declares none. Only declared exposures appear: other BI tools and backend services do not. Under that are two levels upstream and downstream (more on request), and a click on any column lights up its path. Nothing is written until you ask. What it reads was kept when the task ended (`task-manifest.<session>.json`, `last-task.json`), so asking later, after other turns or a restart, still describes that task, and it says if a file has changed since. Each session keeps its own copy of the manifest, and copies a day old are removed. A later task that changes a model replaces it. The band's button goes when the next turn starts; `/lineage-report` keeps working.
- **Before a plan.** When Claude puts a plan up for approval, the plugin looks for the models the plan names and adds one line above the dialog with each one's downstream models, tests and exposures, at the model level. It holds nothing back and spends no model tokens. The band shows the same once the dialog closes, until the task's summary takes over. It goes by the names in the plan's text, so a model it mentions may not be one it changes, and "the staging models" finds nothing. Leaving plan mode with shift+tab shows nothing.
- **Warehouse lineage.** When a connected MCP server offers Altimate's `table_lineage` (Snowflake) or `databricks_table_lineage`, the pane adds what the warehouse's query history shows for the model's table. The plugin calls a tool of that name on whichever connected server offers it, itself and without a permission prompt, and sends it the model's `database.schema.table`. It does so only when you ask for the model (`/lineage`, a press in the pane, or `r`), never when the pane follows one of Claude's reads.
- **Claude's own lineage calls.** A `dbt_lineage` result is drawn as a list of edges colored by how each column is derived; ctrl+o keeps the original output under it.

`/lineage <model>[.column]` opens the pane on a model, at any width. When the pane follows Claude's reads on its own, Claude Code draws it only in a terminal at least 144 columns wide (110 once you have opened it yourself); in a narrower one it waits, and a toast and a line above the prompt say so until the pane can open. The remedy: make the text smaller (Cmd -) or type `/lineage`. The pane's line `N tests` counts the tests on the model and on the models downstream of it; with a column selected it counts only the tests on that column of the model (`3 tests on amount`), when the graph says which column each test checks (a manifest over 4 MiB, read through altimate-code, keeps the first count). Lineage calls go to the plugin's MCP server without a permission prompt, or to `altimate tool run` when the server is not available. A manifest over 4 MiB is read through altimate-code (`dbt_lineage` with `include_graph`). Run `dbt parse` or `dbt compile` first; column lineage and reach need compiled SQL. When the shown model's `.sql` file changed after the manifest was written, the pane and the edit note say so: run `dbt compile`, then `r`.

### Team rules

In a project linked to an Altimate workspace, the workspace's approved **team rules** apply to Claude Code itself, not only to the tasks it hands over. With learning on (`altimate learn enable` in the project, or the workspace's "Learn from sessions" if you have made no choice of your own), your corrections can become proposed rules too:

- **At session start** the plugin gives Claude the team rules for this repository, tells it how many proposed rules are waiting for you, and reports the owner's reviews of your proposals since your last session (approved, or rejected with the reason).
- **When you correct Claude** ("no, we never use FLOAT for money") the correction is recorded locally. When you correct it on the same topic in two sessions, or correct a team rule it was given, altimate-code words a proposed rule after the turn, in the background.
- **"Remember this as a team rule: …"**, said to Claude, waits as a proposal the same way. It needs "as a rule" or "team rule" followed by ":" or "-": "remember to run the tests", a question, or "don't remember this as a team rule" is just part of the conversation. A task handed to altimate-code decides this as an altimate-code session does.
- **`/altimate-code:rules`** shows the proposals waiting for you, the team rules, and the status of the rules you proposed. For each proposal you choose: send it to the workspace owner's review (or approve it, if you are the owner), edit the wording, save it as a memory, or "Not a rule". Nothing reaches teammates until the owner approves it. It also lists your skill and knowledge requests to the workspace (waiting, approved, rejected with the reason, or removed), read-only: withdrawing a request or removing an approved skill or knowledge base happens in the Altimate web app, altimate-code's TUI (`/rules`) or its VS Code extension.
- **Decisions on your skill and knowledge requests** are told to Claude at session start, and shown to you as a toast once each: at session start and every 15 minutes while an interactive session runs. This needs an altimate-code release with `workspace review decisions`; with an older one there are no toasts.
- **`skill publish`** from a session says whether the skill was sent for the owner's review or is already in the workspace.

Rule drafting uses altimate-code's own model (sign in to the Altimate LLM Gateway, or set a provider in altimate-code): if it has none it can use, the next session start says the check failed. The same commands work in a terminal: `altimate learn proposals`, `altimate learn proposals reply <id> --send`. Proposals from Claude Code sessions are answered only there or with `/altimate-code:rules`: altimate-code's own `/rules` and its VS Code chat panel don't list them. This needs an altimate-code release with workspace rules.

- **Start the session in the linked folder**, or a folder below it. If only a folder inside the repository is linked (a dbt project), a session started at the repository root gets no team rules.
- **A new clone or worktree** gets no team rules until altimate-code has been linked, or run, in that checkout: the link is remembered per folder.
- **The per-turn hooks never block**: they hand off to altimate-code in the background. Session start makes one bounded synchronous call (at most 15 seconds). All of them run only in a linked folder (or below it), as recorded in altimate-code's link cache in your own state directory: nothing in the repository turns them on.
- **`ALTIMATE_LEARN=0`** turns all of it off: the hooks start nothing.

## dbt helpers

What dbt Power User does in VS Code, inside the Claude Code session. Each helper runs the project's own dbt (`.venv` or `venv` in the project folder, `bin/dbt` or `Scripts\dbt.exe`, else `dbt` on `PATH`), one at a time per project, and makes no model-provider call on its own (only **Explain** and **Fix with Altimate Code**, when you press them, hand a failure to Claude or Altimate Code).

The helpers read dbt's artifacts (`manifest.json`, `run_results.json`) from the `target-path` the project's `dbt_project.yml` names, else `target/`. A path set by `DBT_TARGET_PATH`, a command's `--target-path` or a Jinja `target-path` in `dbt_project.yml` is not followed: with one, the check cannot compare columns, model context and the doctor's freshness use the project's folder, and a failed run's nodes are not read from the other folder.

Opening a dbt folder runs two programs the repository supplies, with no action from you: at session start the plugin runs the project's own `.venv/bin/dbt --version` (a `venv` or `Scripts\dbt.exe` too) and the Python that dbt's launcher names, to check them. Trust the folder before you open it in Claude Code.


- **Compile and validate, on every edit.** After Claude edits or writes a model's `.sql` file, the plugin runs the model with `dbt show --limit 1`: dbt compiles it and the warehouse runs it, so a Jinja error or a column the warehouse does not have shows at once. The columns the query returns are held to the ones `schema.yml` documents. The result goes to Claude with the edit's result (it waits up to 30 seconds; a slower check rides on Claude's next tool result) and stays above the prompt. When the query returns no row, or `schema.yml` documents no columns for the model, the check says the columns were not compared rather than calling them a match. When the newest check finds a problem (an older check of another file that lands after a newer one starts does not change the band or open the pane), the **dbt check** pane opens beside the chat (**Details** brings it back): every column the warehouse returned against the ones `schema.yml` documents, or dbt's full error, with **Check again**. When the model's file or its schema file changes afterwards outside Claude's edits (a fix altimate-code made), or Claude edits a schema file or another SQL file (a macro), the check runs again; when the model's file is deleted, its check is dropped. One `dbt show` runs per edit: when the manifest does not name the model, `dbt ls` (which runs no query) gives its name first. Secret values from the `profiles.yml` a dbt command reads (the one its `--profiles-dir` or `DBT_PROFILES_DIR` names, else the one in the folder it ran in, the project's, or `~/.dbt`'s: the string fields of its outputs, and the env vars it names with their defaults) are removed from dbt's messages (errors, logs, the doctor's details, the failure band, Explain and Fix, and the error text kept in the query history) that the helpers show, save or send, and dbt's errors about a `profiles.yml` it cannot read, validate or render are replaced with a fixed message. Identifiers such as schema, database, dataset, project, catalog, warehouse, role and user are not treated as secrets, nor are values under 6 characters or the `type`, `threads`, `method` and `port` fields; query results and manifest facts are shown as they are. The plugin reads those values locally, keeps them in memory only, and never logs, stores or sends them. Redaction is best effort, not a guarantee about every text dbt prints: it matches those values as written, JSON-escaped and in Python's string and byte forms, including values set for the command (`NAME=value dbt …`, `env`, `export`); it cannot catch a value dbt or an adapter prints in another form (encoded, transformed or split), or one the profile builds other than through `env_var`. Other dbt errors (a missing target or profile name, a model's own missing `env_var`) are kept, since they carry no secret. A dbt command Claude runs itself shows its output to Claude unchanged. An error that is not the model's own (a parent not built yet, a connection) does not ask Claude to fix the model or to build upstream models. A model whose path holds a space is not checked (dbt would split its selection and run other models), and when dbt cannot be run at all (no `dbt` on the plugin's `PATH` and none in the project's `.venv`), the check says "dbt could not be run here" instead of an error in the model and tries nothing more until `/dbt-doctor` finds dbt. A column documented with `quote: true` is compared with its exact case. Macros, tests and analyses are not run.
- **A failed run, one press from a fix.** When a `dbt run`, `test`, `build`, `seed`, `snapshot` or `retry` that Claude ran fails (any one of several in a command, even when the shell reports success), the failed nodes (from the `target/run_results.json` the command wrote, together with the errors dbt printed) show above the prompt with **Explain**, which asks Claude to explain each failure without changing files, and **Fix with Altimate Code**, which hands them to `/altimate-code:altimate`. The band stays through **Explain** and **Fix** (the other one can still be pressed) until a passing run of the same kind (or a build) that matches the failed one clears it, or **Dismiss** does: the same selection, the same flags (target, vars, `--full-refresh`, …), the same folder and the same environment variables set in the command. Flags that change only the output or the concurrency, such as `--log-format` or `--threads`, are ignored; for a command that ran several (`dbt run … && dbt test …`), only the same command again, or a whole-project `dbt build` does. A passing `dbt retry` never clears it (the plugin's own check runs `dbt show`, which can rewrite the results a retry re-runs from), and a failing one shows its failure. A run killed before dbt printed its summary clears nothing, and neither does output that cannot be split per command (piped through `tail`, with the headers cut off).
- **Query results in a pane.** (**Min / Default / Max** under the title resize it, here and in the lineage pane, and the choice is kept across sessions. Default is the widest dock beside the chat; Min narrows it to a quarter; Max is as wide as Default and taller above the prompt; a size you drag yourself wins, though the marker still moves. Claude Code takes at most 45% of the width for a dock, so no pane can be full width.) Rows from a `dbt show` Claude runs (when one command runs several different `dbt show`s, no preview from it is saved), and from `/dbt-show <model>` or `/dbt-show select …` (50 rows), open as a table beside the chat. **Re-run** runs it again: Claude's own `dbt show` with the same flags in the same order, from the folder Claude ran it in, with the same limit (a bare `dbt`, as an activated venv or `uv run` leaves it, runs as the project's own dbt; a command that depended on its shell (a variable, `~`, a glob, an environment prefix, or other commands before it than `cd` and activating the project's `.venv`) offers no Re-run), or your `/dbt-show` query, **Bookmark** keeps it, and the pane lists your bookmarks and the last 20 queries. They are kept on this machine in Claude Code's plugin store, up to 50 rows each (a cell cut at 200 characters, 32 KiB a query), across sessions; **Clear history** forgets every query that is not bookmarked, while bookmarks (at most 50) keep their rows. When the plugin store refuses a write, the oldest unbookmarked queries are dropped and it tries once more.
- **Model context, before Claude guesses.** When Claude reads a model's `.sql` file, the model's materialization, relation, columns (types, descriptions and tests), model tests, parents, children and depth upstream and downstream, from `target/manifest.json`, go to Claude with the file, once a turn. A manifest over 4 MiB is read for that model through the project's Python. A file newer than the manifest is said to need `dbt parse`.
- **An environment doctor at session start.** The plugin checks dbt-core, the Python that runs it, whether the profile's adapter is installed, whether the packages in `packages.yml` (or `dependencies.yml`, when it declares `packages:`) have been installed, and whether the manifest is older than the project's files, lists a file that is gone, or misses a file added to a folder that changed since the last parse (from the folders and `target-path` dbt_project.yml names, and the profiles.yml dbt itself reads). Anything wrong shows above the prompt with **Run dbt parse** or **Run dbt deps**, and Claude is told with your first prompt. `/dbt-doctor` opens the checks in a pane and also tests the warehouse connection (`dbt debug`), which session start never does.

Compile and validate runs a query on your warehouse after every model edit (`dbt show --limit 1`). On a warehouse that bills by bytes scanned or wakes a suspended warehouse for it, that costs money. Set the plugin's `dbt_mods` option to false (in `/config`) to turn all of the helpers off.

### altimate-dbt

When Claude mentions `altimate-dbt`, it is the dbt command line that comes with altimate-code (`npm i -g @altimateai/altimate-code`, the same install as the plugin's engine). It finds your dbt project folder, Python environment and warehouse adapter by itself, and altimate-code's agent uses it instead of the raw dbt tool for better error messages. Its commands include `init`, `doctor`, `compile`, `build`, `run`, `test`, `deps`, `columns <model>`, `graph` (lineage) and `execute "<sql>"` (a query through the dbt adapter). You do not need to run it yourself: Claude and the altimate-code agent call it when a task needs it, and the plugin's own dbt helpers above do not depend on it. See [altimate-dbt in the altimate-code docs](https://docs.altimate.sh/data-engineering/tools/dbt-tools/#altimate-dbt-cli).

## Warehouse savings check

`/savings [connection]` checks your Databricks and Snowflake connections for savings, each with four of the checks Altimate's hosted product runs. On Databricks: Classic or Pro SQL warehouses that would cost less as serverless, warehouses larger than their queries need, idle all-purpose clusters, and scheduled or continuous jobs running on all-purpose clusters. On Snowflake: high idle time, warehouses that could be downsized, underutilized clusters and frequent restarts. With both kinds of connection, one `/savings` checks both. A pane beside the chat shows each finding with what it rests on and a monthly range (at list price, or at your Snowflake account's own credit price when the check can read it), each resource counted once at its largest saving.

- **Slim first.** Each run opens the pane slim: one header for every connection checked, the total (each resource counted once, at its largest saving), and the three resources with the largest saving across both platforms (by the high end of their monthly range), each on one line at its largest finding, with the one measured fact you can check in your own console and its Draft the fix button. Below them, how many other findings there are and what the resources not shown add to the total, so the three amounts shown plus that line make the total; then how many more checks Altimate runs on these platforms, Share report and Close. A drafted fix's line stays under its finding, or shows on its own once its finding has cleared. **Show all** opens the full detail, a section per platform: every finding with all its evidence, the what-ifs, the checks that did not run and Run again; **Show fewer** goes back. Every run, refused or not, and every new session open slim again. The Share report page always has the full detail.

- **It runs only when you ask.** A run queries your warehouse and can start a stopped one, which costs you money. So nothing here runs the check by itself: the status line, the notes under tool calls and the pane all read the last answer, kept on this machine for 7 days (`$.store`) or until you run `/savings` for that connection again. An answer shows only where its connection reaches the same workspace or account, so one project's results do not appear in another's.
- **Status line.** At session start the plugin asks altimate-code which connections you have (`warehouse_list`, which reads its config and reaches no warehouse) and shows the platforms plus `/savings`. After a run it shows the monthly range, with the age of the answer once it is a day old.
- **A note under the tool call.** When a tool call runs on a warehouse with a kept finding, one quiet line under its row gives the warehouse, the strongest fact and the monthly range. That covers altimate-code's `sql_execute` and `sql_explain` (over MCP or `altimate tool run`), by the connection they name, and `dbt run` / `dbt build`, by the target in `profiles.yml` (on Snowflake, only when the connection names its account). To know which warehouse a connection runs on, the plugin reads `connections.json` for Databricks' `http_path` and workspace host and Snowflake's `warehouse` and `account`. It uses nothing else from that file, and keeps only the host or account, beside the answer, so the answer appears only where the same workspace or account is connected. A connection set only through an `ALTIMATE_CODE_CONN_*` variable has none of this, so its notes rely on the warehouse its own run went through. A `dbt` line that follows a `cd` in an earlier command is read against the session's project.
- **Draft the fix.** Each finding has a button that puts the change in your prompt box (serverless, a smaller `cluster_size`, auto-termination, or a job cluster) for Claude to draft against your bundle or Terraform, or as CLI JSON. Nothing is sent until you press Enter, and nothing is applied.
- **After a drafted fix.** Draft the fix keeps the resource, what it cost a day and the date. A later `/savings` says one of: `measuring (n of 7 days)`, with no change seen yet or with one seen; nothing changed over a whole window, so no saving is claimed; or, once a whole window has passed since the change was seen, its observed spend a day before and after, from billing. The two amounts come from different weeks, so a quieter or busier week moves them too: the pane shows what was billed and never calls the difference saved. A draft changes nothing and the plugin cannot see when a change lands, so days are counted from the first run that saw a new size or type. A fix that changes neither (auto-suspend, a cluster maximum) gets no saving: when its finding clears, the pane gives the cost before and after and says it cannot tell whether your change did that. Clusters and jobs say whether they are still flagged, since their cost afterwards is not in the answer.
- **Spend since a change.** The first run that flags a warehouse remembers its size, type and cost on this machine (`$.store`), all from that run. A later run that finds the size or type changed shows its observed spend a month before and after the change, and names only the settings read both times. A setting the CLI did not list then is taken from the first later run that reads every setting the baseline knew, finds none changed and gives a cost: that run's read, date and spend replace the first run's, so the comparison starts from it. The two amounts come from different weeks, so a quieter or busier week moves them too: they are what was billed, not a measured saving.
- **What if.** For each flagged warehouse, press serverless or any smaller size to see what it would cost a month and whether its cores still cover what its queries need.
- **Checks that did not run.** The pane names the hosted product's other checks for that platform, each with a count from your own run of what it would look at, and one button opens Altimate's sign-up page. The address carries nothing from your run.
- **Share report.** Writes the findings, evidence, what-ifs and checks not run to one self-contained HTML page (`target/.altimate-lineage/savings-report.html` in a dbt project, else `~/.altimate-code/savings-report.html`) and opens it. Nothing is uploaded; it stays on your machine until you send it.
- **At the right moment.** Editing a bundle's `databricks.yml`, a YAML file under `resources/` whose top-level `resources:` block lists jobs, pipelines, clusters or SQL warehouses, or a Terraform file with a line that starts with a `databricks` provider, resource or data source, or running a `databricks` warehouses, clusters, bundle or jobs command, shows a line above the prompt: the flagged resource's saving when the file names it, else, when the file mentions warehouses or clusters (a command always counts), a once-a-session offer of `/savings`. Nothing runs by itself.
- **What runs.** altimate-code's `finops_databricks_savings` and `finops_snowflake_savings` tools, with your own connection (the first of each platform, or the one named). The Databricks check reads seven days of system tables (`system.billing`, `system.compute`, `system.query`, `system.lakeflow`) on that SQL warehouse, which Databricks starts if it is stopped and bills while it runs, so it runs only when you type `/savings` or press a button for it. System tables cover every workspace of the account they can see, so one connection checks all of them, and Show all names each finding's workspace. A check whose tables the connection cannot read is named as not checked; the others still report.
- **What it needs.** altimate-code 0.12.12 or later, which has the Databricks tool and assessment mode, and a Databricks connection whose `http_path` is a SQL warehouse (`/sql/1.0/warehouses/<id>`) with an access token that can read those system tables. Snowflake needs an altimate-code that has `finops_snowflake_savings`; an older one is told to update while the Databricks section still shows.
- **What leaves your machine.** The plugin first asks `altimate --version`, which starts no telemetry, and does not start an older altimate-code, or a source build (which prints `local` whatever its age), for the check or for listing connections. It then runs them with `ALTIMATE_TELEMETRY_DISABLED=true`, `ALTIMATE_ASSESSMENT_MODE=true` and `--no-daemon`, so neither altimate-code nor altimate-core sends usage telemetry for them. `/savings` sends no plugin usage event either: typing it, its buttons and opening its pane are not counted, and the check's queries and results never go to Altimate. The findings stay in the pane until you send a Draft the fix request. Claude can also run the same tool itself; its answer then reaches your model provider like any other tool result.

## Settings

The plugin has seven settings, shown when you enable it (`userConfig` in `.claude-plugin/plugin.json`). All are optional: Claude Code may report them as "not set", and each then takes the default below. `dbt_mods` is used by the dbt helpers, `maxScanBytes` by the scan check (BigQuery, Snowflake, Databricks), `healthBlocksPush` and `healthConfigPath` by the project health check, the two comments settings by team comments, and `show_edit_impact` by the per-edit impact note.

| Setting | Default | What it controls |
| --- | --- | --- |
| `dbt_mods` | on | Turns all of the dbt helpers (above) off when false. |
| `maxScanBytes` | 10737418240 (10 GiB) | A dbt run, build or show estimated to scan more bytes than this is held until you approve it with `/allow-scan` (0 never holds; at least 0). On BigQuery the estimate is a dry run; on Snowflake and Databricks it is the query planner's (`EXPLAIN`): Snowflake's bytes after pruning, an upper bound, and Databricks' table sizes, which a run usually reads less of. A query with no estimate (a Databricks table without statistics) runs, with a note saying why; other warehouses are never held. |
| `healthBlocksPush` | off | When on, `git push` is refused while the project health check finds new issues in the models you changed, and while the check cannot run (altimate-code missing, or without `dbt_health`) or has not finished. Off, the issues are only shown. If the first check of a session lands after you changed a model, that model's existing issues count as new (the baseline then lacks them). The reverse also holds: a model you drop from a schema file before that first check lands has its new issues taken as existing, so a push is not held for them. |
| `healthConfigPath` | empty | The DataPilot health check config file, relative to the dbt project. Empty uses the default checks. |
| `commentsPollSeconds` | 900 | How often, in seconds, the team's comments on shared docs are fetched again in an interactive session (30 to 86400). |
| `commentsInContext` | on | Whether the open comments on a model Claude reads or edits are added to its context. |
| `show_edit_impact` | off | When on, the note on what a model edit reaches downstream is also shown in the transcript; off sends it to Claude and the debug log only. |

## Example prompts

Once installed, try these in Claude Code (or prefix any of them with `/altimate-code:altimate`):

1. **Column-level lineage** — *"Trace the `revenue_usd` column in `models/marts/fct_revenue.sql` back to its sources, and list every downstream model that would be affected if I change its rounding."*
2. **Warehouse cost analysis** — *"Give me a cost report for our Snowflake account: the ten most expensive queries this month and any warehouses that look over-provisioned."*
3. **Cross-dialect validation** — *"Compare `prod.orders` in Snowflake with `analytics.orders` in BigQuery row-by-row using `id` as the key, and summarize any mismatches."*
4. **dbt test generation** — *"Generate dbt tests for `models/staging/stg_orders.sql`, including unit tests for the CASE/WHEN logic."*

## Data handling

MCP tools and `tool run` run locally under your credentials; tool results Claude reads enter the Claude Code conversation and reach its model provider. Neither makes an LLM call of its own.

The dbt helpers run the project's dbt on this machine. What they add to Claude's context (dbt's errors, column names, the manifest's facts about a model) reaches its model provider like any tool result. The rows of the Query results pane are kept on this machine only, in Claude Code's plugin store, until you clear them (bookmarked queries keep their rows through **Clear history**, and turning `dbt_mods` off does not delete them; see PRIVACY.md).

The plugin counts its own use anonymously through the altimate-code CLI's usage telemetry (`altimate-code tool report-event`; no network connection of the plugin's own): `plugin_session_start` at each session start, with the plugin and altimate-code versions, the OS and a random install id kept in the plugin's Claude Code store; and `plugin_feature_used` when `/lineage`, `/dbt-show`, `/profile-ctes`, `/scan-cost`, `/comments`, `/sql-graph`, `/health`, `/runs` or `/to-model` opens, or the cost check or the health push gate holds or allows a command, with the feature's name and the outcome. `/savings` is not counted: it sends no usage event. No session id, project, model, column or file names, SQL or session text, and none of the identifiers altimate-code's other telemetry carries (account, machine id). Set `ALTIMATE_TELEMETRY_DISABLED=true` to turn it off (with altimate-code's other telemetry). An altimate-code that predates these events drops them silently. Every event and field is listed in [PRIVACY.md](../../PRIVACY.md#plugin-usage-events).

Delegating a task with `altimate run` passes your prompt text to the altimate-code CLI, which sends it to your configured LLM provider — the Altimate LLM Gateway by default, or your own provider (BYOK), in which case Altimate never sees it. Warehouse credentials and query results stay on your machine.

## Troubleshooting

| Symptom | Fix |
|---|---|
| Neither `altimate-code` nor `altimate` on PATH | `npm i -g @altimateai/altimate-code` (Node 20+), then run `altimate` once to configure your provider. |
| MCP tools missing from the session | Managed settings may disallow MCP servers, `altimate-code` may not be on PATH (curl and PowerShell installs older than v0.12.8 expose only `altimate`), or the build lacks `mcp serve`. Claude falls back to `altimate tool run`, so no action is required. |
| `Unauthorized` / `No provider configured` | Run `altimate` (`altimate-code` on npm installs older than v0.7.1) to open the TUI and reconfigure your provider via `/connect`, or set the provider API key env var. |
| Task hangs for several minutes | Open `altimate` (`altimate-code` on npm installs older than v0.7.1) to check for a pending prompt in the TUI, or re-run specifying a known-good model. |
| Empty result | The task may be too ambiguous — restate with the target table, expected columns, or time window. |
| `UNKNOWN_USER` / `Database does not exist` mid-run | The CLI connects but your warehouse credentials don't match this project — reconfigure warehouse auth in the `altimate` TUI (`altimate-code` on npm installs older than v0.7.1) or `profiles.yml`. |
| `Not signed in to Altimate` | Run `altimate auth login -p altimate-backend --method "Altimate LLM Gateway"` (`altimate-code` on npm installs older than v0.7.1). |
| Answers ignore your workspace's skills or knowledge | Run `altimate workspace status` in the project. If it isn't linked, ask Claude to link it, or run `altimate link` in a terminal. If it is linked, check that your CLI has `tool run --workspace-tools` (`altimate upgrade`). |
| `Altimate account or workspace changed` | The sign-in or link changed since Claude read the workspace. Claude re-reads `workspace_context` and retries once; if it repeats, ask Claude to check `altimate workspace status`. |
| Workspace engine `needs_engine` | Let Claude run `altimate workspace-client engine-install`, or run it yourself. |
| Team rules don't appear at session start | Check `altimate learn status` in the project: it needs a linked workspace and an Altimate sign-in, and `ALTIMATE_LEARN` not set to `0`. Start Claude Code in the linked folder (or below it), not at the repository root when only a subfolder is linked. Update altimate-code if `altimate learn rules` is an unknown command. |
| Plugin installed but never delegates | Confirm it's enabled: `claude plugin enable altimate-code@altimate-claude-plugin`. |

Still stuck? See [Support](#support).

## Components

- **MCP server** — `.mcp.json` — `altimate-code mcp serve`, read-only by default
- **Skill** — `skills/altimate-code/SKILL.md` — MCP and `tool run` guidance, delegation for long jobs, workspace guidance
- **Agent** — `agents/analyst.md` — read-only data analyst (MCP or CLI)
- **Command** — `commands/altimate.md` — `/altimate-code:altimate` slash command for explicit delegation
- **Command** — `commands/rules.md` — `/altimate-code:rules` to answer proposed team rules
- **Hooks** — `hooks/hooks.json` — SessionStart capability description and workspace skill copy; Stop hook hourly background skill refresh; the team rules hooks (`hooks-handlers/workspace-rules.sh`): SessionStart, UserPromptSubmit and Stop, which call `altimate learn hook <event>` and never fail the session (the per-turn hooks run in the background; session start waits at most 15 seconds); opt-in PreToolUse `warehouse-guard.sh` (needs `ALTIMATE_ROUTE_GUARD=1`)
